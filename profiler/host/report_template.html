Kernel profile

  • Percentages are shares of guest CPU cycles, not wall-clock time. Time spent outside the guest, such as e1000 register writes handled by QEMU, isn't counted, so functions that are slow because of device exits look cheaper than they are.
  • Idle time doesn't appear, because halted CPUs don't count cycles.
  • Samples can land a few instructions after the code that caused them, because the interrupt arrives through KVM.
  • The profiling build adds frame pointers and disables sibling calls, so its code differs slightly from a normal build.
  • Fast functions without a frame pointer, such as memset and memcpy, can lose their immediate caller.
  • Functions inlined at -O3 are attributed to their caller unless debug info resolves them.
  • Observer effect: sampling itself costs CPU time, so the profiled load runs slightly slower than an unprofiled one. The overhead figure above estimates this inside the guest only.
  • Percentages include the [userspace] bucket, so kernel functions look small next to it. Zoom into a kernel frame to compare them.
  • The counter counts core clocks, not TSC time, so the real rate on a busy CPU was measured at 1% to 24% above the request. Sampled busy time is overestimated by that much, and the overhead share understated by the same factor.
